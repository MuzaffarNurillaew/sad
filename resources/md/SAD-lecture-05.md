What is a requirement?
Something that the product must do or a quality that the product must have.
1. Functional requirements – are things the product must do.
Examples: Ability to create a new blog post, edit existing posts, allow users to login, etc.
2. Non-functional requirements – are the qualities the product must have.
Examples: Prevailing color must be our corporate color, website should be able to process 100
concurrent users, interface must be easy to use, etc.
3. Constraints – are global issues that shape the requirements.
Examples: Must be available in TAS-IX only, product must comply with ISO XXXX standard, legal
constraints, etc.
NOTE: Collected/documented requirements must be unambiguous and non-vague.

eXtreme Programming
What is meant by “taking things to their extremes”?
Taking “good practices” to extreme.
For example:
• Code review improves code quality → make code review continues →
Pair programming!
• Tests reduce errors, improve code → test everything → Cover all your
code with unit tests, integration tests, etc.
• Etc.
Business Information Systems 11

XP: Values
1. Communication – promote among the team members, also
involve end users actively.
2. Simplicity – design the simplest solution. Code for today, not
tomorrow. "You ain’t gonna need it" (YAGNI) approach.
3. Feedback – from unit tests, acceptance tests, customer.
4. Courage – to change your code or throw it away.
5. Respect – your peers. Don’t commit a change that breaks
tests or compilation. Make sure everyone feels appreciated
and heard.

XP: Rules
Planning • No functionality is added early.
• User stories are written. • Refactor whenever and wherever possible.
• Release planning creates the release schedule.
Coding
• Make frequent small releases.
• The customer is always available.
• The project is divided into iterations.
• Code must be written to agreed standards.
• Iteration planning starts each iteration.
• Code the unit test first.
Managing • All production code is pair programmed.
• Give the team a dedicated open stand-up. • Only one pair integrates code at a time.
• Set a sustainable pace. • Integrate often.
• A stand-up meeting starts each day. • Set up a dedicated integration computer.
• The Project Velocity is measured. • Use collective ownership.
• Move people around.
Testing
• Fix XP when it breaks.
• All code must have unit tests.
Design • All code must pass all unit tests before it can be
released.
• Simplicity.
• When a bug is found tests are created.
• Choose a system metaphor.
• Acceptance tests are run often and the score is
• Use CRC cards for design sessions.
published.
• Create spike solutions to reduce risk.
