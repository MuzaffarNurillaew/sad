# Development Methodology

FarmTrack splits into two halves with opposite requirement-stability profiles, and that split — not a general preference for one methodology — drives the choice below. The core record-keeping module (FR-01 to FR-05, NFR-01, NFR-02, NFR-03, NFR-05) already has fixed, fully-elicited requirements from Coursework 1's catalogue: mortality logging, batch-tagged feed recording, per-batch profit, slaughter headcount, and the bazaar-agent cross-check were all derived from interviews and observation already completed, not from guesses still to be tested. The extension track (FR-06 voice entry, FR-07 environment monitoring, FR-08 remote lighting, FR-09 density analysis) is the opposite: each depends on unproven hardware (temperature/humidity sensors, a lighting relay, cameras) or unvalidated AI accuracy (voice parsing of a farm director's spoken Uzbek/Russian, density estimation from footage), so its real scope cannot be fixed until those are tested against the actual farm.

## Scrum vs Waterfall against this case, not in the abstract

Applied to the core module, Waterfall fits the available evidence: because FR-01 to FR-05 and their NFRs are already closed questions, a single sequential pass (design the five record types once, build once, validate once against the director) carries no requirement-discovery risk that staged increments would protect against. It also avoids the one resource FarmTrack genuinely lacks — a sprint cadence the director can attend. He has no desk and no fixed schedule; his availability is unscheduled 15–30 minute house checks and Telegram/phone contact, not a diary slot for a recurring sprint review.

Applied to the extension track, Waterfall is the wrong choice for the same reason it was right for the core: committing to one sequential build before FR-06's voice-parsing accuracy or FR-07/FR-08's sensor/relay hardware have been tried against the farm risks building to a spec that has to be discarded once those assumptions fail late — Waterfall's known failure mode when requirements are not actually stable. Scrum's iteration would catch this earlier, but Scrum's protection comes from its ceremonies (sprint planning, review, retrospective), and those assume a team and a counterpart able to attend them on a boundary. CW2 is solo development for one non-technical, unscheduled stakeholder: there is no second team member for a daily check-in, and no fixed point at which the director can reliably sit for a sprint review. Running the core module under Scrum would add backlog grooming and sprint-review overhead to five requirements that are already fixed in the catalogue — paying iteration's cost for scope that no longer needs to be iterated.

| | Core module (FR-01–05, NFRs) | Extension track (FR-06–09) |
|---|---|---|
| Requirement state | Closed — fixed in CW1's catalogue | Open — hardware/accuracy unproven |
| Right fit | Waterfall, single pass | Iterative, but not sprint-boxed |
| Why Scrum underperforms here | Ceremony overhead with no remaining discovery risk to justify it | No team or schedulable stakeholder to run ceremonies with |

## The proposed hybrid

Neither methodology fits FarmTrack whole; the two halves need different treatment, so the proposed approach is a deliberate construction from both rather than an off-the-shelf choice:

- **Core module — Waterfall.** Requirements → design → build → one validation pass against the director, in that order, with no planned iteration, because CW1 already closed requirement discovery for this scope and there is no stakeholder capacity to spend on review ceremonies that buy nothing further.
- **Extension track — Kanban, not Scrum.** Each extension (a voice-parsing proof of concept, a sensor read, a lighting relay trigger, a density-estimate script) sits as one card pulled at a time into a single "in progress" slot, validated against hardware or director feedback whenever either is actually obtainable, with no fixed sprint boundary forcing a review the director cannot commit to. A one-at-a-time work-in-progress limit matches solo capacity directly — there is no second developer to parallelise across, so a limit any wider than one is cosmetic. Kanban is chosen over Scrum specifically because Scrum's entire value in this situation would be the forced stakeholder check-in at the sprint boundary, and that check-in has no one scheduled to attend it; continuous pull with ad hoc validation captures the same incremental-risk reduction without manufacturing a ceremony around an unavailable attendee.

This hybrid is case-built, not generic: it exists because FarmTrack's two halves fail the two standard methodologies for different, specific reasons — fixed scope with no ceremony capacity on one side, unstable scope with no schedulable team or stakeholder on the other — and each half is assigned the one approach that matches its actual failure mode rather than a single methodology applied uniformly across both.
