# Requirements Catalogue

These are requirements for the proposed information system, each traced to a specific gap already documented in the business case, requirements gathering, or data flow diagram sections. Non-functional requirements are classified under this module's eight categories; none are filed under a separate "constraints" bucket.

## Functional Requirements

| Requirements ID | Requirements Name | Requirement Description |
|---|---|---|
| FR-01 | Direct Worker Mortality Logging | Let any worker record a chick death directly, at the moment it is found and tagged to the house, rather than reporting it verbally to the director for later handwritten entry — the two-person, verbal-then-written path the business case already calls approximate. If the same death is logged twice (e.g. by two workers in one house), flag the duplicate rather than double-counting it. |
| FR-02 | Batch-Tagged Feed Delivery Recording | Record each feed delivery's quantity, supplier, and date against the specific house and batch it is for, and calculate feed used per bird for that batch — closing the gap where feed use today only reaches the notebook and is never read back, so cost per bird is unknown. If a delivery arrives while the two houses are mid-batch on different schedules, assign it to the correct house rather than one shared pool. |
| FR-03 | Per-Batch Profit Calculation | Calculate and display a running profit figure separately for each house's open batch, rather than pooling costs and revenue into one running total — directly answering the director's own request that pDaftar separate figures by batch. Since the two houses can be mid-batch on different schedules, let any cost or sale be entered against whichever specific batch is currently open for that house. |
| FR-04 | Recorded Slaughter Crew Head Count | Record the hired crew's reported head count for a session as a discrete, timestamped figure tied to that session's payment, rather than converting a verbal count straight into payment with nothing kept to check later. If a later recount disagrees with the original figure, let the director log a correction with a note instead of silently overwriting it. |
| FR-05 | Bazaar Agent Total Cross-Check | Record the bazaar agent's reported kg total alongside the worker's own weighing tally for the same session, and flag automatically if the two don't match, rather than the director manually comparing them before calculating what's owed. If one figure arrives before the other, hold the comparison as pending rather than calculating payment from a single, unconfirmed total. |
| FR-06 | Intelligent Voice-Entry Logging | Let the director speak a record aloud (an amount, a date, a reason) and have the system parse it into the correct category, date, and reason fields automatically, rather than requiring manual structured entry — directly addressing the director's own complaint that small, incidental costs go unrecorded because assigning them by hand takes more effort than he has in the moment. If the system cannot confidently parse a field from what was said, flag it for manual confirmation rather than guessing. |
| FR-07 | Real-Time House Environment Monitoring | Display live temperature and humidity readings for each house on the director's phone, sourced from sensors tied to the cameras already installed, rather than requiring a manual visual check to judge conditions — a gap the director named directly. If a reading crosses a range the director sets as abnormal, flag it rather than leaving the deviation to be noticed on the next check. |
| FR-08 | Remote House Lighting Control | Let the director turn each house's lighting on or off remotely from his phone, rather than requiring someone physically present to operate the switch — matching the director's own request for remote control. If connectivity is lost mid-command, confirm whether the change actually took effect rather than assuming it did. |
| FR-09 | ML-Based Flock Density Analysis | Analyze camera footage to estimate flock density per house and surface a slaughter- or feeding-timing recommendation from it, rather than the by-eye judgment the business case already describes — the specific analysis the director asked for. Flag low-confidence estimates (e.g. poor camera visibility) rather than presenting them with the same confidence as a clear reading. |

## Non-Functional Requirements

| Requirements ID | Requirements Name | Requirement Description |
|---|---|---|
| NFR-01 | Usability: Phone-First Field Use | The system must be fully usable one-handed from a phone, with no task requiring a desk or fixed screen — matching the director's own statement that a future tool should be phone-based since he is rarely at one fixed location. Usability must hold in outdoor daylight conditions typical of a farm visit, not indoor use only. |
| NFR-02 | Operational: Multi-Worker Field Entry | Any of the farm's 2-4 workers must be able to enter a record (e.g. a chick death or feed delivery) directly from either house, without routing it through the director first, since today every observation reaches a record only after passing through him verbally. Entries made in both houses within the same few minutes must be kept as separate house-tagged records, not merged. |
| NFR-03 | Security: Director-Only Financial Visibility | Batch costs, revenue, and profit figures must be visible only under the director's own login, with no worker role able to view them — the director already treats this data as confidential, having declined to share or photograph the paper notebook or pDaftar for this report. A worker entering a record with a cost field (e.g. a feed delivery) must not see that field's value in their own view of the entry. |
| NFR-04 | Performance: Same-Visit Payment Calculation | Entering a session's head count must return the crew's payment figure within the same visit, before the crew leaves — matching how payment is currently settled on the spot. Since the director is rarely at one fixed location, an entry made without a live connection must still be captured and synced later, rather than requiring a connection at the moment of entry. |
| NFR-05 | Maintainability and Portability: Arbitrary House/Batch Count | The data model must support any number of houses and concurrently running batches without a redesign, since the farm already runs two houses on independent ~60-day cycles. A new house must be addable by the director through configuration (name and capacity) alone, not by changing code. |

The director has confirmed he would use and pay for a system covering these ten requirements.
